## 3. 识别测试

### 3.1 测试集与统计口径

- 已注册对象：4 名（s001–s004），测试照片 38 张。
- 未注册对象：4 张。
- 注册/测试严格分离：每人 5 个注册向量，测试照片不参与注册。
- 质量门控开启，全局阈值 0.30。
- 被质量门控拒绝或检不出人脸的样本一律计入拒识率，不做静默剔除。

指标定义：

- **准确率（全部样本）** = 正确识别数 / 全部已注册样本数
- **准确率（接受的样本）** = 正确识别数 / 通过门控并放行的样本数
- **拒识率 FRR** = 已注册对象未正确识别 / 全部已注册样本
- **误识率** = 已注册对象被认成其他已注册对象 / 全部已注册样本
- **误识率 FAR** = 未注册对象被放行 / 全部未注册样本
- **检测漏检率** = 完全检不出人脸的样本 / 全部已注册样本
- **平均响应时间** = 目标设备上逐帧处理时间的平均值

### 3.2 总体指标

| 指标 | 数值 | 说明 |
|---|---|---|
| 准确率（全部样本） | **89.5%** | 34 / 38 |
| 准确率（接受的样本） | **100.0%** | 34 / 34 |
| 拒识率 FRR | **10.5%** | 4 / 38，全部为 s004 远距离样本 |
| 误识率 | **0.0%** | 0 / 38 |
| 误识率 FAR | **0.0%** | 0 / 4 未注册样本被放行 |
| 检测漏检率 | **0.0%** | 38 张全部检出人脸 |
| 质量门控拒绝 | 4 张 | 人脸占比 0.88%–1.95%，低于 2% 阈值 |

> 说明：4 张 s004 样本并非“检测器完全没检出”，而是检出后因人脸占比低于 `min_face_ratio=0.02` 被质量门控拒绝。因此本报告把“漏识率”按 FRR 计，同时单列检测漏检率，避免混淆。

### 3.7 低光补充测试

测试素材：手机低光视频 `data/VID_20261017_214015.mp4`。

抽测 60 帧，其中 41 帧检出人脸，指标范围：

| 指标 | 范围 | 阈值 | 结果 |
|---|---|---|---|
| 检测分数 | 0.45–0.86 | 0.60 / 0.45 | 检测成功 |
| 对齐人脸亮度 | 14.2–19.4 | 40 | 全部低于阈值 |
| 对齐人脸模糊度 | 27.7–83.8 | 60 | 多数低于阈值 |
| 人脸占比 | 0.17–0.43 | 0.02 | 全部通过 |

结果：

- 质量门控开启：全部判为 `LOST`，无法识别。
- 关闭质量门控（`--no-quality`）：同一视频可以识别。
- 结论：CLAHE + 低阈值回退检测在低光下仍能检出人脸，说明检测增强有效；瓶颈在于**增强只作用于检测阶段，对齐后的人脸仍按原图评估**，亮度/模糊低于门控阈值。门控的拒绝是失败安全设计，避免不可靠条件下误认。
- 后续改进：将对齐后的人脸做 CLAHE/伽马增强后再做质量评估与特征提取；或在低光场景下自适应放宽亮度阈值，并在样本集上重新标定 FAR/FRR。

### 3.8 多帧投票与双模式验证

当前实现为固定 7 帧窗口、70% 一致确认。在低帧率/快速换人的对比视频上：

| 模式 | 帧数 | 身份跳变 | 确认帧 |
|---|---|---|---|
| 无投票（单帧） | 531 | 49 | 140 |
| 多帧投票 | 531 | 49 | 35 |

分析：

- 该片段 389/531 帧为 `LOST`，投票窗口在 LOST 时清空，7 帧窗口很难填满；因此投票未降低以“有人/没人”为主的身份跳变，确认帧反而减少。
- `eval.py --compare-logs` 的跳变统计包含 LOST，对投票不公平；该结果不能作为“投票有效”的证据。
- 该负面结果促成了双模式设计：
  - **快速模式（单帧）**：会议室签到，响应优先，第一帧达到阈值即确认。
  - **安全模式（多帧投票）**：门禁/敏感场景，稳定优先，最近 7 帧中 70% 一致才确认。
- 7.6 FPS 下，7 帧投票窗口约 0.92 秒；这是安全模式的确认延迟来源，也是后续可改为时间窗口/LOST 容忍的优化点。

## 4. 业务联动

### 4.1 已实现的本地闭环

本模块已实现“识别 → 权限判断 → 模拟开门 → 超时自动关门”的本地闭环，脚本为 `scripts/servo_door.py`。

运行命令：

```bash
cd ~/smart-meeting-face-20261017
.venv/bin/python scripts/servo_door.py \
  --authorized-name Demo01 \
  --mock-servo \
  --open-duration 10 \
  2>&1 | tee /tmp/door_demo.log
```

行为：

| 识别结果 | 权限判断 | 门禁动作 |
|---|---|---|
| 已确认且姓名 = Demo01 | 授权 | 模拟开门，10 秒后自动关门 |
| 已确认但姓名 ≠ Demo01 | 未授权 | 拒绝开门 |
| UNKNOWN（未注册） | 无权限 | 拒绝开门，并保存陌生人截图 |
| LOST / 无人脸 | 无权限 | 不动作，保持关门 |
| 摄像头读取失败 | — | 脚本退出，不默认开门 |

失败路径均不会默认放行，符合任务书“失败时不能默认放行”的要求。`--mock-servo` 不驱动 GPIO，只做模拟开门；如后续接入 SG90，可去掉该参数。

### 4.2 与团队后端的联动

`scripts/iot_reporter.py` 已实现 WebSocket 遥测上报与命令接收：

- 上报 `access_control` 字段：`face_detected`、`face_count`、`authorized`、`access_result`、`door_state`、`servo_angle`、`door_open`。
- 后端下发 `COMMAND` 后 3 秒内回 `COMMAND_ACK`。
- 断线每 5 秒重连。
- 失败结果明确：UNKNOWN/未授权为 `denied`，无人脸为 `pending`，不会默认授权。

## 5. 问题与风险

1. **目标设备帧率 7.6 FPS**：纯 CPU 推理，画面有可感知卡顿；签到场景可用，但实时性不如开发机。
2. **低光召回不足**：门控亮度/模糊阈值拒绝低光人脸；检测增强有效，但对齐人脸未增强。
3. **固定帧窗口投票在低帧率下不占优**：7 帧窗口约 0.92 秒，快速换人时无法累计；已改为双模式按场景选择。
4. **无活体检测**：打印照片可能通过；视频与报告不声称防伪，报告中列为局限。
5. **隐私与授权**：演示使用 `Demo01` 等编号；旧日志中的真实姓名不应出现在交付物中；出镜人员需同意。
6. **Pi 端完整准确率复评待补**：当前 89.5% / FAR 0% 来自开发机完整评测（同一模型与配置）；树莓派端完成了运行验证与响应时间实测，但样本集尚未在 Pi 上重跑。
7. **团队后端未联调**：登录/预约/前端闭环待后端服务可用后验证。
